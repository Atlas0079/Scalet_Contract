# 玩家体验审视与撤离循环提案

审查日期：2026-09-07。基于 Demo 1.4.2 的代码、设计规范和实际 Pygame 渲染界面。

本文保留 1.4.2 的体验审查及后续方向。用户已同意改进方向，并补充宏观与微操搜索、完成后暂停分配、黄色物资标识、现场拿取及后续 Godot 迁移要求；详细规则与 1.5 已实现范围见 [通用交互与物品规则](interaction_and_loot.md)。下文“当前证据”均指审查时的 1.4.2；1.5 已实现场内搜刮与部分界面修正，撤离、仓库和跨局永久伤亡尚未实现。

## 1. 本轮已确认的方向

1. 保留玩家同时指挥多个角色、实时推进、自由战术暂停。
2. 主体循环为：搜集物资 → 判断继续深入的风险 → 撤离 → 整备成长 → 再次出战。
3. 未带出的装备和物资会丢失。阵亡队员永久失去，需要招募新人。
4. 允许分批撤离。撤出的队员离开当前战局，留在场内的队员继续由玩家指挥；第一批撤离不结束整局。
5. 沿用已经对齐的指挥原则：微操优先于自动交战；接管某个宏观参与者会取消整个关联宏观行动。允许八方向移动，单侧角落阻挡允许斜穿、双侧受阻禁止斜穿。
6. 延续现阶段不实现人质解救、护送的范围。本提案也不把拖拽伤员作为下一版前置需求。
7. 尸体应放到最近的可用格。角色可以跨过尸体，但经过时减速；地面散落物品不阻挡移动。
8. 宏观和微操都支持搜索物品。搜索读条完成后自动暂停、打开分配界面；分配给谁，谁就必须实际到交互位置完成拿取。
9. 可拾取地面物品和未打开容器为亮黄色，打开过的容器为暗黄色。颜色不能替代已取空、未搜完和物品剩余状态。
10. Pygame 仅用于功能演示，后续迁移 Godot。规则和动作组合优先于为具体物品编写专用行为。

新的评价标准：玩家是否清楚命令会影响谁、能否准确读懂危险、是否能在物资收益与队员损失之间作出决定。清空所有敌人不再适合作为普通战局的通用结束条件。

## 2. 应先解决的现有操作问题

### 2.1 菜单会吞掉暂停按钮点击——已复现

场景：游戏运行中打开右键菜单，直接点击顶部暂停按钮。实际只关闭菜单，时间继续推进。原因是菜单外点击处理先于 HUD 按钮处理，并提前结束该次事件。

建议：暂停属于全局控制，菜单打开时也必须一次点击生效；空格保持全局有效。打开普通上下文菜单继续沿用不自动暂停的规则，避免打开菜单本身偷偷改变时间状态。

证据：[菜单事件处理](<C:/MyResearch/Scarlet Contract/combat_demo/rendering/pygame_view.py:301>)。独立 SDL 测试进程已复现，未操作用户正在运行的游戏。

### 2.2 个人菜单与快捷键的执行者不同——已复现

场景：全选四人，右键 3 号打开个人指令，按 R。菜单点击会给 3 号下令，但快捷键给原来选中的四人下令；H、X 同样使用原选择。玩家正在看“3 号个人指令”，却可能停止整队。

建议：保留右键个人菜单不改变原选择的既有要求。菜单打开期间，R/H/G/Q/X 等角色指令使用菜单所标明的执行者；菜单关闭后恢复原选择的快捷键范围。菜单标题、地面描边和快捷键提示必须指向同一人。全局暂停和镜头控制仍保持全局作用。

证据：[个人菜单](<C:/MyResearch/Scarlet Contract/combat_demo/rendering/pygame_view.py:140>)、[快捷键](<C:/MyResearch/Scarlet Contract/combat_demo/rendering/pygame_view.py:403>)。

### 2.3 “停止所选人”和删除节点没有完整表达整组后果——已确认

侧栏“停止 X”的提示是“取消所选队员计划”；单人队列中的删除按钮只有“×”。若该人或节点关联宏观行动，实际取消整个关联行动。个人右键菜单已经有接管影响提示，不能笼统称为系统完全没有提示；缺口在其他入口没有复用它。

建议：所有取消入口在悬停时高亮受影响成员，明确显示“取消接待室突入 · 影响 1、2、3、4”。原地停步按钮命名为“取消计划并停步”，说明正在走的单格段会先完成。常规战术命令不增加确认弹窗；真正终止战局、放弃未撤离队员才使用明确确认。

证据：[停止按钮](<C:/MyResearch/Scarlet Contract/combat_demo/rendering/pygame_view.py:661>)、[节点删除](<C:/MyResearch/Scarlet Contract/combat_demo/simulation/orders.py:455>)。

### 2.4 多人移动的预览不等于最终分配——已确认

拖动移动时，四条预览路线都指向同一个点击格；提交时系统才为各人分配不同停靠格。在门口、掩体边缘，最后谁站哪里直接影响遮挡与射界。当前预览无法可靠回答这个问题。

建议：预览和提交使用同一套落点分配结果，显示四个带编号的落点和各自方向。不可完成整次多人移动时，预览立即说明哪个人不可达，不能只画一个正常颜色的目标括号。

证据：[移动预览](<C:/MyResearch/Scarlet Contract/combat_demo/rendering/pygame_view.py:590>)、[实际落点分配](<C:/MyResearch/Scarlet Contract/combat_demo/simulation/orders.py:178>)。

### 2.5 批量补给按钮过度使用整组拒绝——已复现

场景：全选四人，只有 3 号缺弹。按 R 会被 1 号“弹匣已满”阻止，结果无人换弹；消息也没有指出是哪个人导致拒绝。对玩家来说，“让需要换弹的人换弹”是合理预期。

建议：区分明确协同与便捷批量操作。突入、同步行动继续整体校验；侧栏批量换弹、包扎只作用于当前符合条件的人，按钮写“换弹 · 1 人”“包扎 · 2 人”，悬停列出执行者和跳过原因。若这些执行者关联宏观行动，仍遵守整组接管，并预显受影响范围，不偷偷保留旧任务。

证据：[批量调用](<C:/MyResearch/Scarlet Contract/combat_demo/rendering/pygame_view.py:125>)、[整组物品校验](<C:/MyResearch/Scarlet Contract/combat_demo/simulation/orders.py:194>)。

### 2.6 关键伤势被长队列挤走——已确认

底部队员卡常驻弹药、指令、闪光和包扎，但没有伤势概览。身体详情只在单选时出现在行动队列后面，队列占用高度后可能不绘制。永久死亡规则下，玩家不应为了知道谁腿伤、谁重伤而逐个翻队列。

建议：底部每张卡固定保留伤势与行动能力警告、弹药、负重、当前职责。诸如“腿伤 · 移动变慢”优先于平时的“保持观察”。完整身体详情放单独展开面板，不跟行动队列争同一段滚动区域。暂未实现的持续失血等状态不得画成正在生效的机制。

证据：[身体详情](<C:/MyResearch/Scarlet Contract/combat_demo/rendering/pygame_view.py:697>)、[队员卡](<C:/MyResearch/Scarlet Contract/combat_demo/rendering/pygame_view.py:782>)。

### 2.7 消耗品数字的含义不一致——已确认

个人菜单显示“总数 / 预留数”，队员卡闪光弹显示“可用数（预留数）”。同一枚已预约闪光可能在一个位置显示 1，在另一个位置显示 0。玩家需要自己推算。

建议：统一显示“可用 0 · 已安排 1”，展开查看总量；“已安排”能定位到消耗该物品的计划。未来背包也沿用这套含义。计划编辑时的预计可用量与实际持有量应分别命名。

证据：[菜单数量](<C:/MyResearch/Scarlet Contract/combat_demo/rendering/pygame_view.py:144>)、[队员卡数量](<C:/MyResearch/Scarlet Contract/combat_demo/rendering/pygame_view.py:797>)。

### 2.8 失败理由、事件历史和菜单稳定性需要补齐——部分已复现

单人选择“突入”只得到“当前选择没有可达入口，或该方式不可用”，隐藏了至少两人的真实限制。事件内部保留历史，界面只显示最新一条；多队同时行动时，门锁、受袭、取消等消息会互相覆盖。

另已复现一个菜单异常：键盘进入子菜单后，用鼠标移到根菜单的普通条目，使分支关闭，再按 Enter，残留的键盘层级会造成 TypeError。此项属于应修复的稳定性缺陷。

建议：失败消息说明具体人、对象和原因；可操作的替代方案只在确实有效时提供。增加可展开的近期事件列表，重要事件能点选定位。键鼠切换需保持当前焦点与实际显示层级一致。

证据：[宏观禁用理由](<C:/MyResearch/Scarlet Contract/combat_demo/rendering/pygame_view.py:179>)、[事件显示](<C:/MyResearch/Scarlet Contract/combat_demo/rendering/pygame_view.py:718>)、[菜单键鼠状态](<C:/MyResearch/Scarlet Contract/combat_demo/rendering/widgets.py:50>)。

## 3. 面向撤离循环，应重新设计的体验

### 3.1 主目标与结算

当前最后一名敌人死亡后立即成功，HUD 明示全局消灭数 /10。这符合当前清敌关卡规则，但会把新循环变成寻找最后一个敌人的清场作业，也向玩家提供超出现场观察的整体敌情。

建议：普通战局移除全局敌人数，顶部显示委托进度、场内队员数、已撤离人数和已知撤离点。击杀不自动结束战局，消灭所有敌人也不自动银行入账。新物资只有随携带者撤离才进入仓库。已完成委托与已交付委托分别记录。

结算展示带回物资、带出与阵亡队员、损失装备和委托交付，不以击杀数作为主要奖励目标。具体委托可以要求消灭某个明确目标，不能据此恢复全图清敌的默认规则。

当前证据：[结算触发](<C:/MyResearch/Scarlet Contract/combat_demo/simulation/world.py:386>)、[顶部计数](<C:/MyResearch/Scarlet Contract/combat_demo/rendering/pygame_view.py:638>)。

### 3.2 “搜索”必须分成两件事

当前房间搜索访问观察点，不取物资；突入自动串联进入和整房搜索。今后玩家可能只想穿过接待室去撤离，整房检查会增加不必要的耗时和暴露。

建议把宏观行动拆为可读阶段：“到门外 → 处理门 → 进入 → 检查威胁”。默认突入仍可包含检查威胁，但草稿必须允许将结束点改为“进入后警戒”。这是对旧版强制整房搜索规则的明确提案，需要后续设计确认后才替换实现。

“搜索容器”单独表示翻找物资。房间只记录“上次检查威胁 02:10”，容器记录“未搜索 / 搜索中 / 已搜索”；已知容器的物资是否取走独立记录。不显示暗示绝对安全的房间状态，也不根据尚未发现的容器生成“本房间全部搜完”的全知数字。

### 3.3 搜刮需要分工，不能让全队围着箱子

用户要求宏观和微操都提供物品搜索。微操指定某人搜索某个对象；宏观指定区域与参与者，组织同样的接近、搜索和拿取动作。不得把所有参与者自动挤到同一个柜子旁。搜索本身不要求背包有余量，拿取才检查容量。

搜索完成自动暂停并显示物资分配；确认分配只建立计划和预约。玩家把 A 搜出的武器交给 B 后，必须由 B 接近容器并完成拿取，实物才归 B。宏观内部安排属于任务分工，外部微操仍遵守接管规则。

具体对象选择、暂停、分配、计划归属、预约、中断与颜色状态以 [通用交互与物品规则](interaction_and_loot.md) 为准，替代此前只做单容器微操的建议。

### 3.4 一张小队物资面板，四份真实携带关系

建议用一张面板查看“附近容器 + 各队员携带物”，避免玩家反复开关四个背包。每件物品有明确携带者；队员死亡、撤离、负重均按此归属处理。

下一版先采用列表与重量容量，不加入物品旋转拼格。价值、重量、任务用途直接可见，能比较“带走药品还是再装一把枪”。自动分配只在玩家勾选的实际参与者中进行，预显携带者、拿取顺序和拿取后负重；不自动丢弃旧物品、不自动跨地图转移。

队内交换必须通过人物实际接近和转移动作完成。拾取阵亡队员的装备可作为容器交互复用，不能让死者物资自动传到其他人背包。已经撤离的人和仓库不能远程接收场内物品。

当前证据：[个人耗材与预约](<C:/MyResearch/Scarlet Contract/combat_demo/simulation/items.py:44>)；旧规范明确禁止交换和尸体拾取，此限制需随新循环移除。

### 3.5 自动开火规则会决定潜入是否成立

当前自动开火 / 禁止开火足以支持清敌测试；撤离玩法里，看到可绕过的敌人就自动射击，可能替玩家作出不想打的交战决定。

建议提供清楚的射击纪律：“自由开火”“受袭还击”“保持停火”。“受袭还击”只允许针对本人已看见并识别的敌人还击，来弹线索不能提供透视射击权限。具体触发和恢复条件需要单独定义后实现，不能用含糊的“谨慎模式”代替。

微操移动仍优先于自动射击，不重新引入被交火钉在原地的问题。当前有效移动时明确显示“移动中 · 暂停射击”；玩家主动停止移动后才恢复该人的射击纪律。探索时应能看到各成员是否会主动开火，多选混合状态显示“规则不一致”。

### 3.6 分批撤离是人员与物资的真实离场

建议将“前往撤离点”和“执行撤离”区分。前者只是移动或小队行进，不跨越撤离边界；到达后在撤离面板提交明确成员名单，显示他们带走的物资和仍留场的队员。

离场动作有倒计时；暂停冻结倒计时。参与者离开撤离范围或死亡，本批次尚未完成的倒计时取消，剩余成员需重新提交，避免名单暗中缩减后直接离场。受击本身不强制终止，只要角色仍活着且符合撤离点条件。倒计时完成后，本批次存活参与者正式离场，携带物进入仓库；不再能为场内小队观察、射击或下令。

队员卡保留“已撤离”位置，避免 1–4 编号因离场重排；此卡只读，不能让数字快捷键误选其他人。场内人数降为零才结束整局；仍有人留场就继续指挥。主动放弃剩余战局必须另设明确入口，列出将永久失去的队员和装备。

这些是建议的执行细则；用户已确认的是允许分批撤离且不自动结束战局。倒计时长度、撤离范围和各撤离点条件仍需在下一份实现规格中定值。

### 3.7 永久死亡需要读得懂的危险与可恢复的经营

建议把队员名字、技能和装备归属从固定的先锋 / 侧翼标签中分离。阵亡结算明确记录该人和未收回装备。新招募者继承的是玩家分配的战术席位，不继承死者身份与成长。

重伤活人沿用当前可慢速行走的规则，下一版先不增加背人、拖拽或倒地救援。受伤带来的速度和操作能力损失必须能在卡片上读懂，撤离计划应预估最慢成员而非默认所有人同速。

局外首先实现仓库、基础交易、治疗、招募与出战配装。建议永久提供一名无成长新人和一套无转售价值的基础装备作为低资源恢复途径，避免全灭后连再次出战都做不到；它不返还阵亡队员或原装备。出战人数建议允许 1–4 人，不能强迫破产玩家先凑齐四人。这个恢复规则属于经济设计建议，尚未确定。

### 3.8 尸体、可交互物与地面掉落

“可交互”描述对象允许玩家做什么，不是与“地面物品”互斥的分类。门、柜子、尸体、掉落物和撤离点都能交互，但动作不同。建议采用以下玩家可理解的对象定义：

| 对象 | 所在位置 | 可执行动作 | 物资归属 | 移动影响 |
|---|---|---|---|---|
| 门 | 两格之间的边 | 打开、踹开、组织突入 | 门本身不持有战利品 | 按门状态阻挡 |
| 固定物资容器 | 家具所在格 | 搜索、查看、取走、存放 | 物品属于此容器 | 是否阻挡由家具本身决定；搜索不改变阻挡 |
| 尸体容器 | 确定的地面格 | 搜索、查看、取走、存放 | 保留死者身份及未取走的装备物品 | 可跨过，经过减速 |
| 地面物品堆 | 确定的地面格 | 查看、拾取、放下 | 同格散落物归入同一地面物品堆 | 不阻挡、不减速 |
| 撤离区域 | 一组标定格 | 查看条件、选择人员、启动撤离 | 完成撤离前不接收物资 | 不额外阻挡 |

尸体不能作为一件普通物品直接装进背包。第一版不增加搬动尸体动作。尸体中的装备仍属于可拿取物品；已被取走的装备不能同时留在尸体清单里。尸体搜空后仍保留尸体和减速效果，显示“已取空”；地面物品堆最后一件物品被拿走后消失。

散落在地面且当前可见的物品直接展示名称与数量，拿取仍需要角色到场；不重复设置“搜索散落步枪”这类翻箱动作。尸体和关闭容器需要搜索才能揭露此前未知内容。发现敌人尸体不等于知道其背包内容。已知己方携带清单可保留情报记录，但不能用记录远程操作尸体物品。

**最近可用格的建议细则：**

1. 站定时死亡，优先死亡所在格；移动途中死亡，以该段起点、终点中距离死亡位置较近的合法格为放置锚点，同距按 y、x 排序。逻辑死亡位置仍用于命中与战报，不因遗体归格改写弹道结果。
2. 可以放置尸体的格必须属于地图有效地面，不能有阻挡移动的固定家具。关闭门和墙作为边界，尸体不能穿过它们寻找落点。
3. 优先选没有其他尸体的格。活人可以经过尸体，地面掉落也不阻挡，所以活人和散落物品不排斥尸体放置；尸体位置不会在活人靠近后重算。
4. 锚点已被另一尸体占用时，按从锚点出发的八方向最短路径距离寻找下一可用格，同距按 y、x 排序。斜向遵守已确认的单侧允许、双侧阻挡规则；摆放距离只算横纵 1、斜向 √2，不计尸体减速。
5. 建议将散布半径限制为路径距离 2 格，避免密集伤亡时将尸体搬到远处。半径内没有空的尸体位置时，留在锚点，同格保留多个独立尸体容器，交互列表分别列出身份；不删除物资、不挪到墙另一侧。半径 2 格属于待确认初值。
6. 死亡只生成一次尸体容器，解除死者命令和物品预约，剩余装备与物资归属转到该尸体。角色档案保留死亡记录，不再拥有第二份可操作库存。

**经过尸体的建议细则：**角色中心位于尸体格内时才应用减速，离开该格恢复；同格多具尸体只应用一次减速，不相乘到几乎无法通过。减速倍率尚未确定，正式实现前需定值。斜向侧邻格上有尸体不等于阻挡角落，也不应因经过其角点额外减速。寻路应比较预计耗时，能在跨尸体与绕行之间取舍；基础几何距离仍是横纵 1、斜向 √2。

**拾取与点击的建议细则：**

- 玩家点击对象后，角色走到同格或一条可交互直边相邻的格才能搜索、拾取或转移；墙和关闭门阻止隔边交互，不允许斜角隔墙摸箱子。同格交互仅适用于不占满格子的尸体和地面物品堆，固定家具从相邻合法格操作。
- 身上物品、固定容器、尸体、地面物品堆、局外仓库中，同一物品只能归属其中一处。队内交接与放下物品都必须完成现场动作后才转移归属，暂停时不能直接完成转移。
- 放下的散落物优先落在执行者当前合法地面格，同格有物品堆则合并清单；不改变尸体位置。尸体与地面物品堆同格时保持两个对象，不能悄悄把地面枪支塞入尸体库存。
- 同一点击区域只有一个可交互对象时直接打开它的菜单；重叠多个时先显示简短目标列表，例如“门 / 3 号队员 / 尸体 2 具 / 地面物品 3 件”，悬停对应条目高亮实体，再进入动作菜单。已知有多个目标时不能靠一个固定优先级使其中某个永久点不到。
- 尸体轮廓、物品堆符号、固定容器标记使用不同形状；选中后显示名称和动作。远离视野后只保留已知记录，不能实时看到未知物资变化或未发现的尸体。

这一节把用户已经确认的尸体归格、跨尸体减速、散落物不阻挡，扩展为待确认的完整交互提案；尚未修改当前死亡绘制、移动或库存实现。

## 4. 战斗界面的建议布局

| 区域 | 常驻信息 | 交互原则 |
|---|---|---|
| 顶部战局栏 | 委托、时间状态、场内 / 已撤离人数、撤离入口 | 暂停始终可点，不受菜单和选点工具阻挡 |
| 中央地图 | 当前能见范围、已知地形、队员职责、所选命令的落点与朝向 | 路线预览必须等于提交结果；不显示隐藏敌人总量 |
| 底部队员卡 | 身份、伤势警告、弹药、负重、射击纪律、当前行动 | 生存信息不因队列变长消失；已撤离卡只读 |
| 右侧情境面板 | 当前对象、执行者、动作及后果 | 没有同步任务时隐藏 A/B 放行区；有容器时显示搜索与拿取；有撤离任务时显示名单 |
| 可展开事件栏 | 受袭、发现威胁、伤亡、命令拒绝、撤离与取消记录 | 显示发生者和时间，点击可定位；重要事件不被下一条静默覆盖 |

视觉继续使用线条与 VHS 风格。应降低网格、扫描线和远处蓝图的对比，让队员状态、入口、可互动对象更醒目。墙、关闭门、打开门、窗、低家具、高家具应使用固定符号并提供悬停说明；不能只靠相近颜色让玩家猜可走、可见、可射击。

区分“蓝图已知”“亲自观察过”“当前可见”。现在未探索家具也被画在蓝图上，这是现有信息规则，不是单纯的渲染错误。转向搜刮玩法后，建议保留墙体与房间的初始蓝图，容器内容必须搜索才知道；容器本体是否预先标注要依任务情报明确规定。

## 5. 用一局小场景验证新循环

建议沿用灰港建筑制作首个撤离测试局：四人从南侧进入，一处委托物品、一条额外收益支路、两个可选择的撤离点，补充少量容器。提供一处始终可用的撤离点和一处在场内开启的捷径撤离点，具体位置与条件在关卡规格中单独定值。

示例体验：两人检查接待室，一人搜柜、一人看走廊；拿到委托物品后，仓库支路仍有额外收益，但一名队员腿伤且弹药不足。玩家可以让携带者与伤员先撤离，剩下两人继续冒险，也可以全队保守撤出。前一批离场后，战局仍运行，仓库已记录带回物资，剩余两人的死亡不会追溯扣除已撤出的收益。

首版验收重点：

- 不消灭全部敌人，也能带回物资完成一局；击杀最后敌人不会强制结算。
- 搜索者需要实际到场，其余人的警戒职责可见且可被接管。
- 暂停中能编排搜索、拿取和撤离，但不会获得进度或物资。
- 物品携带者、负重、阵亡遗留和撤离入库始终一致。
- 第一批撤离后，剩余队员能继续行动；编号和选择不发生错误跳转。
- 阵亡队员永久离开名册，已撤离队员和物资保留。
- 一次全灭后仍有明确的招募与再次出战路径。
- 当前已确认的微操优先级和整组接管原则继续成立。

## 6. 建议顺序

第一步：修复菜单暂停、执行者范围、键鼠菜单异常；统一预览与实际落点，补齐伤势常驻和取消影响提示。

第二步：实现一局能完整闭合的容器搜索、个人携带、分批撤离、仓库入库、永久阵亡和招募流程。优先验证玩家是否愿意在拿到收益后主动撤离。

第三步：再扩展物品种类、负重取舍、射击纪律和委托。复杂弹匣管理、背包拼格、护甲弹药大全、藏身处生产、动态交易市场暂不进入首个闭环。
